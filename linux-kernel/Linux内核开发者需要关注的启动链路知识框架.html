1. 学习层级：哪些必须懂，哪些只需知道

1.1 第一层：内核启动必修

这一层直接影响内核能否启动：

  • CPU 进入内核时处于什么状态。
  • bootloader 传给内核哪些参数。
  • 内核如何找到可用物理内存。
  • 内核如何保留 initramfs、ACPI、EFI runtime、crashkernel 等区域。
  • 内核如何建立早期页表和早期映射。
  • 内核如何解析命令行。
  • 内核如何启动第一个用户态进程。

1.2 第二层：平台和设备初始化必修

这一层影响内核接管硬件：

  • ACPI 如何描述设备、CPU、NUMA、电源和中断。
  • APIC/IOAPIC/MSI/MSI-X 如何把设备中断送到 CPU。
  • PCIe 设备如何枚举、分配 BAR、映射 MMIO。
  • IOMMU 如何限制 DMA。
  • EFI runtime services 如何在内核运行后继续存在。

1.3 第三层：安全与可信启动

这一层影响内核安全边界：

  • Secure Boot 只决定“能不能加载某些启动组件”，不等于系统整体安全。
  • shim、MOK、签名内核、签名模块会影响发行版启动链。
  • Lockdown 会限制 /dev/mem、kexec、BPF、内核调试等高风险接口。
  • TPM PCR 度量会影响自动解密和远程证明。
  • IMA/EVM、dm-verity、fs-verity 等是内核阶段继续建立信任链的机制。

1.4 第四层：硬件上电背景

这一层用于判断问题是否已经到达内核：

  • 完全不亮、不响、无串口：多半还没到固件。
  • 有 BIOS 画面但找不到盘：固件/硬盘/启动项问题。
  • 进入 GRUB 后失败：bootloader、内核文件、initramfs、cmdline 问题。
  • 出现内核日志后失败：才真正进入内核调试范围。

2.2 固件负责什么

固件主要负责：

  • 让 CPU 能执行代码。
  • 让 DRAM 可用。
  • 枚举或初始化必要设备。
  • 构造 ACPI、SMBIOS、内存图等系统描述信息。
  • 根据启动策略加载 bootloader 或 EFI 程序。

通俗说，固件像“开场的舞台管理员”：把灯、电、座位、通道、演员入口准备好，但不负责演完整场戏。

2.3 bootloader 负责什么

bootloader 主要负责：

  • 读取启动菜单。
  • 找到内核文件。
  • 找到 initramfs。
  • 拼接 kernel command line。
  • 按 Linux boot protocol 填写启动参数。
  • 把控制权交给内核。

通俗说，bootloader 像“把剧本、道具和演员送到舞台入口的人”。它不负责内核内部调度、驱动、文件系统挂载的长期逻辑。

2.4 内核负责什么

内核接手后主要负责：

  • 解压自身。
  • 建立页表。
  • 初始化 memblock，再过渡到 buddy allocator。
  • 解析 ACPI/EFI/SMBIOS/设备信息。
  • 初始化中断、定时器、SMP。
  • 初始化 driver model。
  • 挂载 initramfs。
  • 执行 /init。
  • 进入真正用户空间。

通俗说，内核才是“正式接管剧场运营的人”：它不只开门，还要长期管理资源、调度工作、处理异常。

3. 必须掌握的核心知识点

3.1 Linux boot protocol：bootloader 和内核之间的合同

Linux boot protocol 是 bootloader 与内核之间的约定。

它回答这些问题：

  • 内核镜像应该加载到哪里？
  • bootloader 应该把命令行放在哪里？
  • initramfs 的地址和大小怎么告诉内核？
  • 内存图怎么传？
  • 入口地址在哪里？
  • CPU 模式有什么要求？

通俗理解：

boot protocol 就像搬家公司和收货人之间的收货协议。内核不是只要“被复制到内存里”就能运行，还需要知道自己的包裹、说明书、场地边界都在哪里。

内核开发关联点：

  • 早期启动参数解析。
  • 架构相关启动代码。
  • initrd/initramfs 加载。
  • crashkernel、KASLR、内存保留。
  • bootloader 兼容性问题。

3.2 boot_params：内核启动时收到的总清单

boot_params 是 x86 启动时传给内核的重要数据结构。它包含：

  • setup header。
  • kernel command line 地址。
  • initramfs 地址和大小。
  • E820 内存图。
  • framebuffer 信息。
  • EFI 信息。
  • 启动设备和加载器信息。

通俗理解：

boot_params 像开工前递给内核的“交接单”。交接单错了，内核可能把不能用的内存当成可用内存，也可能找不到 initramfs 或控制台。

3.3 E820 / UEFI memory map：哪些物理内存能用

内核不能认为所有物理地址都是 RAM。固件会告诉内核：

  • 哪些是可用 RAM。
  • 哪些是 ACPI 表。
  • 哪些是 MMIO。
  • 哪些是固件 runtime 区域。
  • 哪些是保留区。
  • 哪些是坏内存。
  • 哪些被 initramfs、内核、crashkernel 占用。

通俗理解：

物理地址空间像一栋楼。不是每个房间都能住人，有些是电梯井，有些是机房，有些是消防通道，有些已经被别人占用。内存图就是楼层平面图。

内核开发关联点：

  • memblock 初始化。
  • page allocator 初始化。
  • ioremap() 与 MMIO。
  • ACPI NVS 保留。
  • EFI runtime memory 保留。
  • crashkernel 保留。
  • memory hotplug。

3.4 memblock：buddy allocator 之前的早期内存管理器

内核刚启动时，常规内存管理还没建好，不能马上使用完整的 page allocator。此时用 memblock 管理早期物理内存。

它负责：

  • 记录可用物理内存范围。
  • 记录保留物理内存范围。
  • 为页表、内核数据结构、initrd 保留空间。
  • 在 buddy allocator 初始化前提供简单分配能力。

通俗理解：

memblock 像工地刚开工时的临时仓库管理员。正式仓储系统还没上线，它先用一张清单管理哪些地方能放材料、哪些地方不能碰。

vmlinuz 像一个自解压安装包。bootloader 只负责把安装包放进内存，安装包自己展开成真正运行的内核。

内核开发关联点：

  • 早期页表。

3.6 EFI stub：让 Linux 内核自己像 UEFI 程序一样启动

EFI stub 让 Linux 内核能被 UEFI 当成普通 .efi 程序加载。

它负责：

  • 接收 UEFI image entry。
  • 使用 UEFI boot services。
  • 读取 initrd 和 cmdline。
  • 获取 UEFI memory map。
  • 调用 ExitBootServices()。
  • 跳转到内核解压入口。

通俗理解：

EFI stub 像给 Linux 内核加了一个“UEFI 适配插头”。有了这个插头，固件或 systemd-boot 可以直接把内核当 EFI 程序启动。

3.7 ACPI：x86 平台硬件描述的主渠道

在 x86 PC/服务器上，很多硬件信息不是驱动自己猜出来的，而是固件通过 ACPI 告诉内核。

ACPI 提供：

  • CPU 拓扑。
  • 中断控制器。
  • NUMA 拓扑。
  • PCI host bridge。
  • 电源管理。
  • 热管理。
  • 电池和适配器。
  • 平台设备。
  • IOMMU 信息。

通俗理解：

ACPI 像主板厂商写给操作系统的“硬件说明书 + 一些可执行小脚本”。内核读它，才知道很多设备在哪里、怎么开关、怎么处理中断。

内核开发关联点：

  • drivers/acpi/。
  • platform device 创建。
  • 电源管理。
  • suspend/resume。
  • NUMA。
  • IOMMU。
  • PCI root bridge。

3.8 MADT / APIC / SMP：多核和中断的入口

内核需要知道：

  • 有哪些 CPU。
  • 每个 CPU 的 APIC ID 是什么。
  • IO APIC 在哪里。
  • 外部中断如何路由。
  • 如何发送 IPI 唤醒其他 CPU。

这些信息很多来自 ACPI MADT。

通俗理解：

如果把 CPU 核看成办公室里的员工，APIC 就像每个人桌上的内部电话，IO APIC 像前台总机，MADT 是电话号码簿。

内核开发关联点：

  • SMP bring-up。
  • IRQ domain。
  • 中断亲和性。
  • MSI/MSI-X。
  • 定时器。
  • CPU hotplug。

3.9 PCIe、BAR 与 MMIO：设备驱动访问硬件的基础

PCIe 设备通过配置空间告诉系统自己需要哪些资源。BAR 描述设备寄存器或显存窗口大小。内核最终要把这些物理地址映射成虚拟地址，驱动才能访问。

通俗理解：

BAR 像设备递给系统的一张“我要一个多大柜台”的申请单。系统分配地址后，驱动才能到这个柜台和设备对话。

内核开发关联点：

  • PCI core probe。
  • resource tree。
  • pci_enable_device()。
  • pci_request_region()。
  • ioremap()。
  • MMIO 读写顺序。
  • DMA mask。
  • IOMMU。

3.10 initramfs 与 kernel cmdline：很多启动问题的分界点

内核启动后不一定能直接挂载真正根文件系统。initramfs 提供早期用户空间，用来：

  • 加载存储驱动。
  • 解密磁盘。
  • 组装 RAID/LVM。
  • 发现 rootfs。
  • 执行 switch_root。

kernel cmdline 提供启动策略，例如：

  • root=...
  • console=...
  • init=...
  • rd.luks=...
  • iommu=...
  • crashkernel=...
  • panic=...

通俗理解：

内核像已经醒来的管理员，但真正办公室的钥匙可能在 initramfs 里。cmdline 则像启动时贴在门口的临时指令。

4. 从原文延伸出的“新知识点”通俗说明

本节不是重复原文，而是把原文中对内核开发更关键、但还需要继续学习的知识点补齐。

4.1 start_kernel()：内核 C 世界的主入口

内核经过汇编入口、解压、早期架构初始化后，会进入 start_kernel()。

它大致负责：

  • 初始化锁、调度器、RCU、时间、内存管理等核心子系统。
  • 解析命令行。
  • 初始化 IRQ。
  • 初始化 softirq、workqueue。
  • 启动 initcall 框架。
  • 最终创建 kernel init 线程。

通俗理解：

start_kernel() 像公司正式开门后的总调度会议：各部门按顺序建立起来，之后系统才能接收正常业务。

需要串联的知识：

  • 汇编启动入口。
  • 早期页表。
  • memblock。
  • printk。
  • scheduler。
  • RCU。
  • initcall。

4.2 setup_arch()：架构相关启动初始化

setup_arch() 是架构相关初始化的重要入口。x86 上它会处理：

  • boot params。
  • 内存图。
  • early cmdline。
  • initrd 保留。
  • ACPI/EFI 信息。
  • CPU 信息。
  • NUMA 信息。
  • early ioremap。

通俗理解：

setup_arch() 像内核进入一个具体建筑前的“现场勘察”：先确认这台机器的布局、入口、危险区域和可用资源。

需要串联的知识：

  • x86 boot protocol。
  • E820。
  • EFI memory map。
  • ACPI。
  • NUMA。
  • KASLR。

4.3 early param：很早就生效的内核参数

有些内核参数必须在普通初始化前就生效，例如影响内存、控制台、ACPI、EFI、IOMMU 的参数。

通俗理解：

普通参数像开会时才讨论的设置；early param 像进门前就必须决定的事情，比如走哪个门、灯开不开、哪些区域不能进。

需要串联的知识：

  • kernel cmdline。
  • early console。
  • ACPI 开关。
  • IOMMU 开关。
  • 内存保留参数。

4.4 early console：正式控制台之前的救命日志

早期启动阶段，完整 console 子系统还没初始化。early console 用非常简单的方式输出日志，例如串口、EFI framebuffer、特定 MMIO UART。

通俗理解：

early console 像施工现场的临时对讲机。正式电话系统还没装好，但出问题时至少能喊出来。

需要串联的知识：

  • console=...
  • earlycon=...
  • UART。
  • MMIO。
  • printk 初始化阶段。

4.5 early_ioremap()：早期访问 MMIO 的临时窗口

在完整 ioremap() 机制建立前，内核有时需要临时访问设备 MMIO 或固件表区域，这时会用 early ioremap 类机制。

通俗理解：

正式道路还没修好，early_ioremap() 像临时搭的一块跳板，让内核先过去读一点关键数据。

需要串联的知识：

  • 页表。
  • MMIO。
  • 固件表。
  • fixmap。
  • 正式 ioremap()。

4.6 fixmap：固定虚拟地址映射

fixmap 是一段固定虚拟地址区域，用于映射早期必须访问但物理地址不固定的对象。

通俗理解：

fixmap 像一个固定编号的临时窗口。窗口位置固定，但后面临时接到哪个物理房间可以变化。

需要串联的知识：

  • 虚拟地址。
  • 页表。
  • early ioremap。
  • APIC 映射。
  • EFI runtime 映射。

4.7 ioremap()：把设备物理地址映射给内核访问

设备寄存器位于物理 MMIO 地址，内核不能像普通指针一样直接访问。ioremap() 把这段物理地址映射到内核虚拟地址空间。

通俗理解：

设备寄存器像一排只能通过特殊窗口办理业务的柜台。ioremap() 就是在内核地址空间里开这个窗口。

需要串联的知识：

  • PCI BAR。
  • MMIO。
  • 缓存属性。
  • readl() / writel()。
  • memory barrier。

4.8 readl() / writel()：不是普通内存读写

驱动访问 MMIO 寄存器时通常使用 readl()、writel() 等接口，而不是直接解引用普通指针。

通俗理解：

访问设备寄存器不是读写普通纸张，而是按设备规定的窗口递交命令。顺序、宽度、屏障都可能重要。

需要串联的知识：

  • MMIO。
  • I/O ordering。
  • memory barrier。
  • posted write。
  • DMA 同步。

4.9 IOMMU：给设备 DMA 加边界

DMA 让设备直接读写内存。IOMMU 在设备和内存之间加一层地址转换与权限控制。

通俗理解：

没有 IOMMU，设备像拿到整栋楼万能钥匙；有 IOMMU，设备只拿到被允许房间的门禁卡。

需要串联的知识：

  • DMA mapping API。
  • PCIe。
  • ACPI DMAR/IVRS。
  • VFIO。
  • virtualization。
  • security。

4.10 IRQ domain：把硬件中断号翻译成 Linux IRQ

硬件中断编号和 Linux 内部 IRQ 编号不是一回事。IRQ domain 负责映射它们。

通俗理解：

硬件说“3 号线响了”，Linux 内部要知道这对应哪个设备、哪个处理函数。IRQ domain 就是翻译表。

需要串联的知识：

  • APIC。
  • IO APIC。
  • MSI/MSI-X。
  • device tree 或 ACPI。
  • interrupt controller driver。

4.11 initcall：内核子系统按阶段初始化

内核不是把所有驱动一次性随便初始化，而是通过 initcall 分级执行。

常见阶段包括：

  • early_initcall
  • core_initcall
  • postcore_initcall
  • arch_initcall
  • subsys_initcall
  • fs_initcall
  • device_initcall
  • late_initcall

通俗理解：

initcall 像装修顺序：先打地基，再布线，再装门窗，最后摆家具。顺序错了，后面的东西会找不到依赖。

需要串联的知识：

  • start_kernel()。
  • driver model。
  • bus/device/driver。
  • built-in driver。
  • module init。

4.12 driver model：设备、驱动、总线的统一模型

早期 ACPI/PCI 初始化之后，内核会把设备纳入 driver model。驱动通过总线匹配设备，然后 probe。

通俗理解：

driver model 像招聘系统：设备发布“我是谁”，驱动发布“我能管谁”，总线负责撮合，匹配上就调用 probe。

需要串联的知识：

  • struct device。
  • struct driver。
  • struct bus_type。
  • platform device。
  • PCI device。
  • ACPI companion。
  • device tree。

4.13 firmware bug workaround：内核经常要修固件的锅

现实平台固件可能给出错误 ACPI、错误内存图、错误中断路由或奇怪配置。内核中有大量 quirks/workarounds。

通俗理解：

固件说明书有时写错。内核不能直接罢工，只能针对已知机型或已知错误加“纠错便签”。

需要串联的知识：

  • DMI match。
  • ACPI quirks。
  • PCI quirks。
  • command line workaround。
  • stable kernel regression。

4.14 kexec：不经过完整固件重启直接进入新内核

kexec 允许当前内核加载另一个内核并跳转过去。它绕过大部分 BIOS/UEFI 初始化。

通俗理解：

普通重启像关店、重新开灯、重新检查所有设施；kexec 像不关店，直接换一个经理接手。

需要串联的知识：

  • crashkernel。
  • kdump。
  • Secure Boot lockdown。
  • DMA quiesce。
  • CPU shutdown。

4.15 suspend/resume：启动链路的“反向考试”

系统睡眠和恢复时，固件、ACPI、设备驱动、电源管理都要配合。很多启动时的硬件描述在 suspend/resume 中还会再次用到。

通俗理解：

启动是从零开机，恢复是把暂停的机器重新叫醒。醒来后设备状态、内存、CPU、中断都要对得上。

需要串联的知识：

  • ACPI S-states。
  • device power management。
  • runtime PM。
  • wakeup source。
  • platform firmware。
