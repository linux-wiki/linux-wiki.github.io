1.2 为什么这个阶段重要

这个阶段非常短，但影响巨大：

  • 内核以后能不能安全使用物理内存，取决于早期内存图和 memblock。
  • 早期页表和地址布局错误会导致极早期崩溃，甚至没有普通日志。
  • cmdline 的 early 参数会影响 ACPI、EFI、IOMMU、console、KASLR 等行为。
  • setup_arch() 会把固件交接的信息转成内核自己的模型。
  • start_kernel() 的初始化顺序决定许多核心子系统的依赖关系。

通俗理解：

第一阶段是把人送到楼门口；第二阶段是这个人进楼后先打开灯、确认楼层平面图、标出危险区域、搭临时办公桌，然后才能让各部门进场。

4. 压缩内核和解压器

4.1 为什么内核要压缩

内核镜像通常较大。压缩有几个好处：

  • 减少 /boot 占用。
  • 减少 bootloader 从磁盘读取的数据量。
  • 让内核镜像格式更适合启动协议。
  • 内核可以自己控制解压目标和启动布局。

vmlinuz 中的 z 表示压缩。bzImage 中的 bz 是 “big zImage”，不是 bzip2。

4.2 解压器做什么

解压器不是完整内核，但它已经是一段内核自带代码。它大致负责：

  • 建立能运行 C 代码的最小环境。
  • 获取和检查 boot_params。
  • 找到可用解压目标地址。
  • 处理 KASLR。
  • 避免覆盖压缩镜像、initramfs、保留内存。
  • 解压真正的内核映像。
  • 跳转到未压缩内核入口。

通俗理解：

vmlinuz 像一个自解压安装包。bootloader 把安装包放到内存，安装包自己找空地展开，展开后才是真正运行的内核。

4.3 解压阶段最容易出问题的点

问题可能结果
解压目标和 initramfs 冲突极早期崩溃或后续 initrd 损坏。
KASLR 选择地址异常早期崩溃，调试时可用 nokaslr 排除。
bootloader 传入错误内存图解压器选择了不安全区域。
CPU 特性不满足内核无法继续启动。
早期控制台不可用失败时没有可见日志。

5. KASLR：内核解压位置为什么可能变化

5.1 KASLR 是什么

KASLR 是 Kernel Address Space Layout Randomization，即内核地址空间布局随机化。

它的目标：

  • 让攻击者更难预测内核代码和数据地址。
  • 降低某些漏洞利用的稳定性。

在启动早期，KASLR 会影响：

  • 内核物理解压位置。
  • 内核运行时虚拟地址偏移。
  • 日志中的 Kernel Offset。

5.2 KASLR 为什么影响调试

启用 KASLR 后，同一个符号在每次启动时可能落到不同地址。调试 early crash 时会更麻烦。

6. 早期页表：内核为什么先要能“看见自己”

6.1 物理地址和虚拟地址

CPU 最终会通过分页机制把虚拟地址转换成物理地址。Linux 内核正常运行时依赖虚拟地址空间。

但早期启动时：

  • 完整内存管理还没建立。
  • 完整页表还没建立。
  • 很多地址映射只是临时的。
  • 内核必须先建立足够少、足够可靠的页表，才能继续执行 C 代码。

通俗理解：

页表像一张“门牌号到真实房间”的地图。内核想用自己的固定地址访问代码和数据，必须先把这张地图画出最小可用版本。

6.2 早期页表需要映射什么

至少需要考虑：

  • 内核代码和数据。
  • 解压目标区域。
  • boot_params。
  • initramfs 所在区域。
  • 必要的低端内存。
  • 早期控制台或 MMIO 访问窗口。
  • fixmap 区域。

6.3 为什么页表错误很难调试

页表错误可能发生在：

  • printk 完整可用之前。
  • 异常处理完整可用之前。
  • 控制台完整可用之前。

结果可能是：

  • 直接重启。
  • 黑屏。
  • 三重故障。
  • 虚拟机退出。
  • 只有串口或 early console 有少量日志。

6.4 相关概念

概念说明
identity mapping虚拟地址等于物理地址的映射，早期切换分页时常用。
kernel mapping内核高地址或固定偏移映射。
fixmap固定虚拟地址窗口，用来临时映射早期必须访问的物理地址。
early ioremap正式 ioremap() 前访问 MMIO 或固件表的临时机制。
page table页表，控制虚拟地址到物理地址转换和权限。

7. boot_params 和 setup data

7.1 boot_params 是什么

在 x86 启动协议里，boot_params 是 bootloader 交给内核的重要结构。它常被称为 zero page 相关数据。

它包含或关联：

  • setup header。
  • kernel cmdline 地址。
  • initrd 地址和大小。
  • E820 内存图。
  • framebuffer 信息。
  • EFI 信息。
  • 加载器标识。
  • setup data 链表。

通俗理解：

boot_params 是内核刚接手时拿到的“开工资料袋”。里面有地图、工具箱位置、启动说明、固件表线索和现场边界。

7.2 setup data 是什么

setup data 是对 boot_params 的扩展机制。它可以挂接额外信息，例如：

  • 扩展内存图。
  • EFI 相关数据。
  • device tree blob，特定场景使用。
  • crashkernel 或其它启动扩展信息。

9. memblock：早期物理内存管理

9.1 为什么需要 memblock

内核完整的 buddy allocator 还没初始化前，也需要分配内存：

  • 建页表。
  • 保存内核内部数据结构。
  • 保留 initrd。
  • 保留 crashkernel。
  • 保留 ACPI/EFI 区域。
  • 为早期子系统分配少量内存。

这时使用 memblock。

通俗理解：

memblock 像临时仓库管理员。正式仓库系统没上线前，它先用几张清单管理“哪里能用、哪里已经被占、哪里不能碰”。

10. early param、early console 与早期日志

10.1 early param

有些内核参数必须在普通参数解析前就生效。例如：

  • earlycon
  • console
  • nokaslr
  • memblock=debug
  • efi=...
  • acpi=...
  • iommu=...

通俗理解：

early param 是进楼前就要决定的事情。比如从哪个门进、先开哪个灯、哪些区域不能碰。等普通初始化完成后再设置就太晚了。

11. setup_arch()：架构现场勘察

11.1 setup_arch() 的定位

setup_arch() 是架构相关初始化入口。x86 上它会把 bootloader/firmware 交接的信息整理成内核内部状态。

通俗理解：

setup_arch() 像进入施工现场后的总勘察：确认地形、标出禁区、登记资源、记录设备说明书位置，然后告诉后续部门该怎么施工。

11.2 它大致处理什么

不同内核版本会变化，但主题相对稳定：

  • 保存和解析 boot_params。
  • 处理 kernel cmdline。
  • 处理 initrd 位置和保留。
  • 解析 E820/EFI memory map。
  • 初始化早期内存布局。
  • 设置 memblock。
  • 处理 DMI/SMBIOS 线索。
  • 发现 ACPI 表位置。
  • 处理 CPU 和 NUMA 早期信息。
  • 建立 early ioremap/fixmap 等早期映射能力。
  • 为后续 PCI、ACPI、SMP、IRQ 初始化准备信息。

11.3 setup_arch() 不是什么

它不是：

  • 完整驱动初始化。
  • 完整 ACPI 设备枚举。
  • 完整 PCI 设备 probe。
  • 完整页分配器初始化。
  • 用户态启动。

它更多是“架构级基础资料整理和早期资源登记”。

12. start_kernel()：内核 C 世界总入口

12.1 start_kernel() 的定位

start_kernel() 是通用内核初始化主线。它不是第一条内核指令，但它是进入通用 C 初始化世界后的核心入口。

通俗理解：

start_kernel() 像公司开业第一天的总调度会议。它按依赖顺序让基础部门先成立，再让更上层部门开始工作。

12.2 它大致初始化什么

顺序会随内核版本变化，但可以按主题理解：

  • 设置当前任务和栈保护。
  • 初始化 lockdep、RCU、调试基础设施。
  • 解析 early param 和普通 cmdline。
  • 初始化 CPU、内存、页分配相关基础。
  • 调用 setup_arch()。
  • 初始化 trap/异常处理。
  • 初始化 IRQ。
  • 初始化 scheduler。
  • 初始化 time/timer。
  • 初始化 softirq、workqueue。
  • 初始化 console 和 printk。
  • 初始化 VFS、driver model、各类核心子系统的前置条件。
  • 创建 kernel init 线程。
  • 进入后续 initcall 和用户态启动路径。

12.3 为什么初始化顺序很关键

很多子系统有依赖关系：

子系统依赖示例
printk需要早期缓冲、console 后续注册。
IRQ需要架构中断描述和基本异常处理。
scheduler需要当前 task、时钟、CPU 基础状态。
memory allocator需要 memblock 和内存图整理结果。
driver model需要 slab、kobject、sysfs 等基础设施。
initramfs需要 VFS、rootfs、内存管理等更高层能力。

所以早期初始化不是随便排列的函数列表，而是一个依赖图。

16.1 选择内核后黑屏

可能原因：

  • 日志输出到了别的控制台。
  • 显卡模式切换导致显示断开。
  • 早期页表或解压阶段崩溃。
  • KASLR 触发地址相关问题。
  • bootloader 传错入口或参数。

16.2 早期 panic，日志很少

可能原因：

  • boot_params 不正确。
  • 内存图异常。
  • 解压目标冲突。
  • CPU 特性不满足。
  • 页表或地址映射错误。

建议关注：

  • 是否能打印 Linux version。
  • 是否能打印 Command line。
  • 是否能打印 E820/EFI memory map。
  • 是否启用了 early console。

16.3 initrd 损坏或找不到

可能原因：

  • bootloader 传入 initrd 地址/大小错误。
  • 解压或早期分配覆盖了 initrd。
  • initrd 超出可寻址范围。
  • bootloader 配置加载了错误文件。

定位：

16.4 内存容量识别异常

可能原因：

  • 固件内存图错误。
  • 启动参数限制了内存，例如 mem=...。
  • 大量内存被 reserved。
  • crashkernel 或设备保留区过大。
  • 虚拟机配置问题。

定位：

16.5 EFI runtime 相关异常

可能原因：

  • UEFI memory map 处理异常。
  • EFI runtime 区域映射或保留错误。
  • 固件 runtime service bug。
  • 启动参数禁用了部分 EFI 功能。
