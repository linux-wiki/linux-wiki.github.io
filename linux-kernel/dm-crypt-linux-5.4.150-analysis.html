Linux 5.4.150 dm-crypt 内核模块源码分析

本文基于本机源码树 /data/kernel/linux-5.4.150 分析 Linux 5.4.150 中 dm-crypt 内核模块。核心源码位于：

dm-crypt 是 Device Mapper 的 crypt target。它不直接提供块设备驱动，而是注册一个 DM target，把上层 bio 映射到底层块设备，同时在 bio 数据路径中调用 kernel crypto API 做透明加密和解密。

4. 总体架构

dm-crypt 是一个 bio-based DM target。普通数据路径可以抽象为：

flowchart TD
    A[上层文件系统/块层提交 bio] --> B[Device Mapper core]
    B --> C[crypt_map]
    C --> D{bio 类型}
    D -->|REQ_PREFLUSH 或 DISCARD| E[直接 remap 到底层设备]
    D -->|READ| F[提交底层读 clone bio]
    F --> G[底层读完成 crypt_endio]
    G --> H[kcryptd 解密]
    H --> I[完成原始 bio]
    D -->|WRITE| J[kcryptd 加密]
    J --> K[提交底层写 clone bio]
    K --> L[底层写完成 crypt_endio]
    L --> I

关键设计点：

  • READ：先从底层设备读出密文，再原地解密到原 bio 的页中。
  • WRITE：先分配新的 clone bio 和页，把明文加密到 clone bio，再写到底层设备。
  • kcryptd 工作队列执行加解密。
  • kcryptd_io 工作队列执行部分 IO 提交，尤其是 read clone 分配失败后的延后提交。
  • 单独的 dmcrypt_write 内核线程按 sector 排序提交写，减少乱序写对底层调度器的影响。

7.2 bio 大小和对齐限制

原因：

  • WRITE 需要分配新页保存密文输出，最多按 BIO_MAX_PAGES 处理。
  • integrity metadata 也按当前 bio 的 sector 数分配，过大时需要拆分。
  • bio 起始 sector 和长度必须按 sector_size 对齐，否则无法按固定加密单元生成 IV 和执行 crypto。

7.3 per-bio data

dm_per_bio_data() 在 DM core 中根据 clone bio 地址反推出 target 预留的 per-io 区域。dm-crypt 把 dm_crypt_io 放在该区域开头，后面紧跟 crypto request。

7.4 READ 和 WRITE 分流

READ 尽量直接用 GFP_NOWAIT 克隆并提交底层读；如果失败，排到 io_queue 后用 GFP_NOIO 重试。WRITE 需要先加密，所以排到 crypt_queue。

9.1 分配密文 clone bio

crypt_alloc_buffer() 分配一个新的 bio，并从 page_pool 分配页：

它先用 GFP_NOWAIT | __GFP_HIGHMEM 非阻塞分配；失败后加上 __GFP_DIRECT_RECLAIM 并进入 mutex 保护的阻塞路径。源码注释解释了原因：如果多个线程同时从 mempool 中各自分配一部分页，可能互相等待导致死锁；阻塞 fallback 用 bio_alloc_lock 串行化大块页分配。

14.6 tcw

20. 与 kernel crypto API 的关系

dm-crypt 不实现 AES、XTS、CBC、GCM 等算法本身。它做的是：

  1. 根据 table 中的 cipher 字符串调用 crypto_alloc_skcipher() 或 crypto_alloc_aead()。
  2. 调用 crypto_skcipher_setkey() 或 crypto_aead_setkey() 设置 key。
  3. 每个加密 sector 构造 scatterlist、IV 和 request。
  4. 调用 crypto_skcipher_encrypt/decrypt() 或 crypto_aead_encrypt/decrypt()。
  5. 处理同步完成、异步完成、AEAD 认证错误。

22. 关键行为总结

  1. dm-crypt 是 Device Mapper 的 crypt target，通过 dm_register_target() 注册，不是独立块设备驱动。
  2. READ 先提交底层读，读回密文后原地解密；WRITE 先加密到新分配的 clone bio，再提交底层写。
  3. 加解密以 sector_size 为单位，默认 512 字节，可选 512 到 4096 字节的 2 的幂。
  4. IV 由 crypt_iv_operations 抽象，支持 plain、plain64、essiv、benbi、lmk、tcw、random、eboiv 等模式。
  5. 普通模式使用 skcipher API；integrity:<bytes>:aead 使用 AEAD API，并依赖底层 integrity profile 保存 tag/IV。
  6. 内存管理大量依赖 mempool 和 bioset，目的是在块层和内存回收路径中避免分配死锁。
  7. 异步 crypto 通过 kcryptd_async_done() 收敛，cc_pending 用于等待一个 bio 的多个 sector 全部完成。
  8. 默认写提交会经 dmcrypt_write 线程按 sector 排序，submit_from_crypt_cpus 只让同步加密完成的写绕过该线程。
  9. key 操作要求 target suspended，key wipe 会使 key invalid，resume 前必须重新设置有效 key。
  10. discard 可透传但有安全侧信道风险。
