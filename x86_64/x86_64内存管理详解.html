x86_64 内存管理子模块详解

1. CPU 工作模式演变

x86 处理器自诞生以来先后支持三种工作模式，内存管理机制在每种模式下差异巨大。

模式数据宽度地址线寻址方式特点
实模式16 位20 位段寄存器 × 16 + 偏移无保护，1MB 地址空间
保护模式32 位32 位分段 + 分页（可选）权限控制，4GB 虚拟地址
长模式64 位48 位分段简化（基址=0）+ 强制分页256TB 虚拟地址，现行 64 位标准

1.1 实模式

  • CPU 复位后默认进入实模式。
  • 地址计算：物理地址 = 段寄存器 << 4 + 16 位偏移，产生 20 位物理地址（最大 1MB）。
  • 无保护、无分页，任何程序可直接访问所有物理内存和 I/O 端口。
  • BIOS 启动、MBR 引导阶段均运行在实模式。

1.2 保护模式

  • 32 位 CPU 原生模式，是长模式的过渡基础。
  • 分段：段寄存器不再存储基址，而是存放段选择子（13 位索引 + 1 位 TI + 2 位 RPL），指向 GDT/LDT 中的段描述符。
  • 段描述符（8 字节）包含：段基址（32 位）、段界限（20 位）、特权级 DPL、类型等。
  • 分页：可选启用（CR0.PG=1），启用后线性地址经分页单元转换为物理地址。

1.3 长模式

  • 64 位 CPU 的默认模式（需先经过保护模式过渡）。
  • 段基址强制为 0（CS.D、DS、SS；FS/GS 除外，它们基址从 MSR 或 GDT 获取）。
  • 分页强制启用，不可关闭。
  • 虚拟地址为 48 位，高 16 位用作符号扩展（“规范地址”）。
  • 物理地址最大支持 52 位（实际取决于 CPU 实现，常见 40–46 位）。

2. 分段机制

2.1 段寄存器 (x86_64)

CS  — 代码段
DS  — 数据段
SS  — 栈段
ES  — 附加数据段
FS  — 通用附加段（Linux 中指向线程局部存储 TLS）
GS  — 通用附加段（Linux 中指向 per-CPU 区域；Windows 中指向 TLS）

在长模式下，除 FS 和 GS 外，其余段的基址强制为 0，界限检查关闭。分段主要退化为权限控制和 FS/GS 寻址。

2.2 FS/GS 基址设置

FS 和 GS 的基址通过 MSR（Model-Specific Register）设置：

FS.base  ← MSR_FS_BASE (0xC0000100)
GS.base  ← MSR_GS_BASE (0xC0000101)
GS.base (swap) ← MSR_KERNEL_GS_BASE (0xC0000102)

特权指令 WRMSR / RDMSR 可读写这些 MSR。用户态可通过 WRFSBASE / WRGSBASE 指令修改（需 CR4.FSGSBASE=1）。

2.3 段描述符与 GDT

GDT（全局描述符表）包含多个段描述符（8 字节/项），如下结构：

[63:56]  [55:52]  [51:48]  [47]  [46:45]  [44]  [43:40]  [39:16]  [15:0]
 基址31:24 标志   段限19:16   G     DPL      S     类型      基址23:0  基址15:0
                                  (4位)    (1位)  (4位)
  • DPL（Descriptor Privilege Level）：0–3，段访问所需的最小特权级。
  • S：0=系统段，1=代码/数据段。
  • 类型：代码（可执行）或数据（可读写）、增长方向等。
  • G（Granularity）：0=段限单位 1 字节，1=段限单位 4KB。

LGDT 指令加载 GDTR 寄存器（48 位: 16 位表界限 + 64 位表基址）。

2.4 Linux 内核中的典型段设置

__USER_CS  = 0x33  (Ring 3 代码段，选择子索引 6, RPL=3)
__USER_DS  = 0x2B  (Ring 3 数据段，选择子索引 5, RPL=3)
__KERNEL_CS = 0x10 (Ring 0 代码段，选择子索引 2, RPL=0)
__KERNEL_DS = 0x18 (Ring 0 数据段，选择子索引 3, RPL=0)

3. 分页机制

x86_64 在长模式下使用 四级页表（4-Level Paging），通过 CR3 寄存器链接。

3.1 页表层级

CR3 (4KB对齐物理地址)
  └── PML4 Table (Page Map Level 4)
        └── PDPT (Page Directory Pointer Table)
              └── PD (Page Directory)
                    └── PT (Page Table)
                          └── 物理页帧 (4KB)

每一级表占一页（4KB），每项 8 字节（64 位），正好容纳 512 个条目。因此：

  • 48 位虚拟地址被拆分为 5 个字段： 
    | 符号扩展 [63:48] | PML4索引 [47:39] | PDPT索引 [38:30] | PD索引 [29:21] | PT索引 [20:12] | 页内偏移 [11:0] |
|    16 bits        |     9 bits        |     9 bits        |    9 bits       |    9 bits       |     12 bits       |
    共 16+9+9+9+9+12=64 位。

3.2 页表项结构（PTE / PML4E / PDPTE / PDE）

每级页表项 64 位，字段基本相同：

[63]   NX (No-Execute)       — 不可执行
[62:52] 保留 / PFN 高位
[51:12] 物理页帧号 (PFN)      — 下一级表的物理基址 或 数据页物理基址
[11:9]  保留 / AVL (软件可用)
[8]     G  (Global)           — 全局页，CR4.PGE=1 时不因 MOV CR3 刷新 TLB
[7]     PS (Page Size)        — 仅对 PDE（bit7=1 表示 2MB 页）和 PDPTE（bit7=1 表示 1GB 页）有效
[6]     D  (Dirty)            — 页被写过（由 CPU 自动设置）
[5]     A  (Accessed)         — 页被访问过（由 CPU 自动设置）
[4]     PCD (Cache Disable)   — 禁用缓存
[3]     PWT (Write-Through)   — 写透策略
[2]     U/S (User/Supervisor) — 0=仅 Ring 0 可访问，1=Ring 0-3 均可
[1]     R/W (Read/Write)      — 0=只读，1=可写
[0]     P  (Present)          — 页面存在位，0 则触发 #PF

3.3 大页与巨页

页大小映射层级示例
4KBPT → Page普通小页，缺省粒度
2MBPD → PagePDE 内 PS=1，跳过 PT 层
1GBPDPT → PagePDPTE 内 PS=1，跳过 PD 和 PT 层

大页的虚拟地址结构：

  • 2MB 页：[63:48] + PML4[9] + PDPT[9] + PD[9] + 偏移[21:0] （跳过 PT）
  • 1GB 页：[63:48] + PML4[9] + PDPT[9] + 偏移[30:0] （跳过 PD 和 PT）

优势：减少 TLB 压力、减少页表遍历开销。Linux 内核中 hugetlbfs 和透明大页（THP）均基于此。

3.4 五级页表（启动地址扩展 LA57）

较新的处理器支持 5 级页表（CR4.LA57=1），将虚拟地址扩展到 57 位：

[63:57] + PML5[9] + PML4[9] + PDPT[9] + PD[9] + PT[9] + 偏移[11:0]

增加一级 PML5 Table（Page Map Level 5），支持 128 PiB 虚拟地址空间。

4. 地址翻译全过程

4.1 翻译步骤（以 4KB 页为例）

  1. 取虚拟地址，分解为 PML4 索引、PDPT 索引、PD 索引、PT 索引、页内偏移。
  2. 读取 CR3 获取 PML4 表物理基址。
  3. 查 PML4：PML4_基址 + PML4_索引 × 8 → PML4E。检查 P、R/W、U/S、NX 等权限。
  4. 查 PDPT：PML4E[51:12] << 12 + PDPT_索引 × 8 → PDPTE。同理检查权限。
  5. 查 PD：PDPTE[51:12] << 12 + PD_索引 × 8 → PDE。同理检查权限。
  6. 查 PT：PDE[51:12] << 12 + PT_索引 × 8 → PTE。同理检查权限。
  7. 计算物理地址：PTE[51:12] << 12 + 页内偏移。

4.2 权限检查触发条件

条件异常（#PF 错误码 bit）
P=0（缺页）bit0=1
R/W=0 且 CPL=3 执行写操作bit1=1
U/S=0 且 CPL=3（用户态访问内核页）bit2=1
保留位被设置bit3=1
指令 fetch 命中 NX=1 的页bit4=1
触发 SMEP/SMAP 违规一般保护 GP 或 PF

4.3 缺页异常 (#PF) 处理流程（Linux 视角）

硬件触发 #PF → CPU 压栈 SS:RSP 及错误码 → 进入 page_fault 处理函数
→ handle_page_fault(regs, error_code)
    ├── 地址是否属于内核？→ do_kern_addr_fault()
    │      ├── vmalloc 区域？  → 同步内核页表
    │      └── 否则 → oops/kernel panic
    └── 用户地址？→ do_user_addr_fault()
           ├── 查 mm_struct → find_vma(mm, addr)
           ├── 合法 VMA？→ handle_mm_fault(vma, addr, flags)
           │      ├── 【缺页类型】：匿名页、文件映射页、COW 页
           │      ├── 【分配/填充】：分配物理页 + 设置 PTE
           │      └── 若涉及 swap：swapin
           └── 非法地址 → SIGSEGV

5. TLB (Translation Lookaside Buffer)

5.1 基本概念

  • TLB 是 MMU 内的硬件缓存，缓存虚拟地址→物理地址的映射。
  • 命中延迟：<1 个周期；不命中需遍历 4 级页表（4 次内存访问，约 40+ 周期）。
  • x86_64 处理器通常有独立的 指令 TLB (ITLB) 和 数据 TLB (DTLB)。

5.2 典型 TLB 层级

层级大小覆盖延迟
L1 DTLB~64 项4KB 页~1 周期
L1 ITLB~128 项4KB 页~1 周期
L2 STLB~1500 项4KB+2MB 页~7 周期
L3 STLB可能不实现--

5.3 TLB 刷新

指令作用
INVLPG addr刷新 addr 对应的单条 TLB 条目
MOV to CR3刷新全部 TLB 中非全局条目（若 CR4.PGE=0 则全刷新）
MOV to CR4写 CR4.PGE/PCIDE/SMEP 等位时可能刷新部分或全部 TLB
PCID 机制为每个进程分配 Process-Context ID，减少上下文切换时的全刷新

5.4 带 ASID/PCID 的 TLB 管理

  • PCID（Process-Context Identifier，CR4.PCIDE=1）为地址空间打标签，CR3 低 12 位存放 PCID。
  • 切换 CR3 时，若 PCID 变化，TLB 只刷新该 PCID 对应的条目，全局表项和同 PCID 表项可保留。
  • 大幅降低进程切换开销，是 KPTI（Meltdown 缓解）实现的关键前提。

6. 缓存体系与一致性

6.1 缓存层级

CPU Core
 ├── L1I (32KB, 8路组相联, VIPT)
 ├── L1D (32KB, 8路组相联, VIPT)
 ├── L2   (256KB, 4–8路组相联, PIPT/VIPT)
 └── L3   (数MB, LLC, 共享, 包容/非包容)
  • VIPT（Virtually Indexed, Physically Tagged）：索引来自虚拟地址（低 12 位），标记来自物理地址。对 4KB 页，12 位页内偏移==物理地址，消除别名。
  • PIPT（Physically Indexed, Physically Tagged）：索引和标记均来自物理地址，无别名问题，但需等待 TLB 翻译。
  • LLC（Last-Level Cache，末级缓存即 L3）：多核共享，由 CHA（Caching Home Agent）管理。

6.2 MESI 缓存一致性协议

状态含义
Modified数据被修改，仅本缓存持有，与内存不一致
Exclusive数据干净，仅本缓存持有，与内存一致
Shared数据干净，多个缓存持有，与内存一致
Invalid数据无效，缓存行空闲

核心间通信走 QPI/UPI 总线，Intel 实际使用 MESIF（加 F：Forwarding），AMD 使用 MOESI（加 O：Owned）。

6.3 CACHE LINE（缓存行）

  • 典型大小：64 字节。
  • 对齐访问的最小区块。64 字节内任何字节的修改都会使整行变脏。
  • 避免伪共享（False Sharing）：多个核修改不同变量但落在同一缓存行，导致缓存行反复失效。

7. 内存类型与 PAT

7.1 常见内存类型

类型PAT 索引缓存行为适用场景
WB (Write-Back)0写回，读分配，写分配普通 RAM（默认）
WC (Write-Combining)1不缓存，合并写，直写显存帧缓冲

UC (Uncacheable)6/7不缓存，不复用MMIO 设备
WP (Write-Protected)5共享只读罕见

7.2 PAT 寄存器（Page Attribute Table）

  • 8 项 × 8 位，存放自 PAT0 到 PAT7 的内存类型编码。
  • PT Entry 中 PWT（bit3）+ PCD（bit4）+ PAT（bit12 或 bit7，取决于级别） 三 bit 组合做索引，选择 PAT 表中的内存类型。
  • 控制粒度可从 4KB 到 1GB 不等。

9. 内存保护：SMEP / SMAP / NX / KPTI

9.1 SMEP（Supervisor Mode Execution Prevention）

  • CR4.SMEP = 1 时，Ring 0 代码不能执行位于 U/S=1（用户态）的页面。
  • 阻止内核执行用户态注入的恶意代码（ret2usr 攻击缓解）。

9.2 SMAP（Supervisor Mode Access Prevention）

  • CR4.SMAP = 1 时，Ring 0 代码不能读/写位于 U/S=1 的数据页。
  • 临时绕过 SMAP 的指令：STAC（Set AC flag）、CLAC（Clear AC flag）。
  • Linux 中通过 stac() / clac() 宏在 copy_from_user / copy_to_user 周围使用。

9.3 NX（No-Execute）位

  • 页表项 bit63：NX（Intel 称 XD，AMD 称 NX）。
  • 当 NX=1 时，从该页取指执行会触发 PF。
  • EFER.NXE=1 后才有效（通过 wrmsr(MSR_EFER, ...) 启用）。

9.4 KPTI（Kernel Page-Table Isolation）

  • 背景：Meltdown 漏洞利用 CPU 乱序执行特性，用户态可间接读取内核态内存。
  • 方案：为每个进程维护两份页表——用户态运行时只映射最小内核入口（entry/exit trampoline）；内核页表仅在进入内核时才映射完整内核空间。
  • 进程切换 → 切换 CR3 → PCID 标签隔离 → 降低性能开销。
  • 内核镜像符号：__entry_text_start / __entry_text_end 标记 trampoline 区域。

10. ASLR 与 KASLR

10.1 用户态 ASLR

Linux 启动时对以下区域位置加随机偏移：

  • ELF 可执行文件加载基址
  • mmap 基址（动态库、文件映射）
  • 栈起始地址
  • vDSO 映射位置
  • Heap 起始地址（brk）

随机化粒度：页面大小（4KB 或 2MB/1GB），偏移量通常 8–28 位。

10.2 内核态 KASLR

  • 引导时在物理内存范围内随机选取内核基址偏移。
  • 影响直接映射区、vmalloc、vmemmap 等区域的起始位置。
  • KASLR 熵受物理内存大小限制（通常 9–12 位）。

/proc/sys/kernel/randomize_va_space：

  • 0：关闭所有随机化
  • 1：随机化共享库、栈、mmap；堆不随机化
  • 2：完全随机化（含 brk）

12.2.2.1 SPD — 内存探测的物理基础

SPD（Serial Presence Detect）是焊接在每根内存条上的一颗 EEPROM 芯片（8 引脚，容量 256 或 512 字节），通过 SMBus（System Management Bus，基于 I²C 协议）与主板芯片组通信，出厂时烧录了该内存条的完整参数信息。

SPD 在 POST 阶段的作用：

BIOS 在内存控制器初始化之前，必须先知道插了什么规格的内存，才能正确配置时序和电压。SPD 就是这一信息的数据源。

SMBus 地址分配：

DIMM 插槽 0: SMBus 地址 0x50
DIMM 插槽 1: SMBus 地址 0x51
DIMM 插槽 2: SMBus 地址 0x52
DIMM 插槽 3: SMBus 地址 0x53
(每个插槽对应一个固定地址)

BIOS 读取流程：

BIOS POST → 初始化 SMBus 控制器 → 轮询 0x50-0x53 地址
  │
  ├─ 对每个有响应的地址 (即插了内存条的插槽):
  │    ├─ I²C START → 发送器件地址 + 读命令
  │    ├─ 发送 EEPROM 内偏移 (0x00、0x80、0x100...)
  │    ├─ 连续读取 256/512 字节
  │    └─ I²C STOP
  │
  ├─ 解析 SPD 数据:
  │    ├─ 模块容量 (= DRAM 芯片容量 × Rank 数 × 位宽 / 8)
  │    ├─ 支持的速度档位 (DDR4-2133/2400/2666/3200...)
  │    ├─ 对应时序 (tCL, tRCD, tRP, tRAS, ...)
  │    ├─ 工作电压 (1.2V / 1.35V)
  │    └─ 制造商、型号、序列号
  │
  └─ 将所有 DIMM 容量累加 → 总物理内存量 → 写入 E820 表

SPD 与 E820 的关系：

SPD 读出的是每个 DIMM 的容量参数，BIOS 汇总后知道”一共有多少物理内存”，然后把可用范围以 Type 1 (RAM) 写入 E820 表。E820 再交给操作系统的 memblock → buddy。若 SPD 读取出错，E820 中上报的容量就会缺少，可能导致大量物理内存不可用。

E820 是由 ACPI 规范 定义的 BIOS 中断服务，全称为”获取系统内存映射” (Get System Memory Map)。其作用是在系统启动时向操作系统报告物理地址空间的完整布局——哪些地址段是可用 RAM、哪些被固件/设备占用、哪些存放 ACPI 数据。

1. 工作原理

BIOS 在 POST 阶段通过 SPD (Serial Presence Detect) 读取内存条容量信息，结合平台芯片组寄存器确定全部物理内存。同时 BIOS 本身还需占用部分内存存放 SMBIOS 表、ACPI 表、DMI 数据、SMM 代码等，加之 PCIe 设备的 MMIO 映射需要物理地址空间留出空洞。因此 BIOS 将物理地址区间划分为若干段，每段标注一个类型，保存在一个列表中——这便是 E820 表。

操作系统通过 INT 15h 逐条读取该表：每次传递一个”继续号” (continuation value)，BIOS 返回下一条未读取的条目，直至 continuation value = 0。

8. UEFI 与 E820 的关系

UEFI 固件自身不使用 INT 15h（运行在保护/长模式，无实模式中断），而是通过启动服务 GetMemoryMap() 返回 EFI_MEMORY_DESCRIPTOR 数组。但当使用 EFI handover 协议 或通过 GRUB2 引导时，bootloader 会将 UEFI 的内存映射转换为 E820 格式写入 boot_params.e820_table，确保内核在 setup_arch() 中仍通过 E820 统一处理。

UEFI 内存类型到 E820 的映射关系：

UEFI 内存类型E820 类型
EfiConventionalMemoryE820_TYPE_RAM (1)
EfiReservedMemoryTypeE820_TYPE_RESERVED (2)
EfiACPIReclaimMemoryE820_TYPE_ACPI (3)
EfiACPIMemoryNVSE820_TYPE_NVS (4)
EfiUnusableMemoryE820_TYPE_UNUSABLE (5)
EfiPersistentMemoryE820_TYPE_PMEM (7)

因此在 UEFI 平台 + Linux 内核 的组合中，E820 仍然作为内存管理的统一入口，通过 /sys/firmware/memmap 和 /proc/iomem 可查看完整的内存布局。

    → for_each_free_mem_range()
      → 在 memblock.memory 的空闲部分找到一个足够大的区域
      → 调用 memblock_reserve() 标记为已保留

释放流程:
  memblock_free(base, size)
    → 从 memblock.reserved 中移除该区域
    → memblock.memory 不受影响（整个引导期不会"释放"物理内存）

memblock 提供的关键 API：

API说明

start_kernel() → mm_init() 是内存管理子系统从”早期过渡”到”完全就绪”的分水岭。

12.7.1 mem_init — memblock → buddy allocator

12.7.2 Buddy Allocator 的原理与入口

物理页按阶（order） 管理，order N 表示 2N 个连续页：

free_area[max_order]  ← 每个 zone 中的空闲链表数组

order 10  ┌─→ [2048 页连续块] → ...
order 9   ├─→ [1024 页连续块] → ...
...       ...
order 1   ├─→ [2 页块] → ...
order 0   └─→ [4KB 单页] → ...

分配（alloc_pages）：

alloc_pages(gfp_mask, order)
  → 从目标 zone 中查找 order 的空闲链表
    → 有: 取下链表头，返回
    → 无: 向上 buddy 分裂 (split)
       order+1 的块对半切，一半分配/一半放回 order 链表

释放（__free_pages）：

__free_pages(page, order)
  → 查看 buddy 伙伴是否也空闲
    → 是: 合并为 order+1 的块，递归向上合并
    → 否: 加入 order 链表

Buddy allocator 是物理页框分配的核心，kmalloc、vmalloc、用户态 mmap 最终都通过它获取物理内存。

12.7.3 Slab Allocator — 内核对象缓存

Slab 建立在 buddy 之上，解决”内核频繁分配/释放小对象”的问题：

kmem_cache_create("inode_cache", sizeof(inode), 0, 0, ctor)
  → 创建一个 slab 缓存，专为 inode 对象

kmem_cache_alloc(cache, GFP_KERNEL)
  → 从 slab 缓存中分配一个已预热的 inode 对象

kmem_cache_free(cache, obj)
  → 归还到 slab 缓存（不真正释放物理页）

三种变体：

  • SLAB：传统实现（Solaris 引入，已基本被 SLUB 替代）
  • SLUB：当前 Linux 默认，数据结构更简洁，调试友好
  • SLOB：为极小内存嵌入式设备设计（已移除）

kmalloc/kfree 内部也是基于一组预定义的 slab 缓存：

kmalloc-8, kmalloc-16, kmalloc-32, kmalloc-64,
kmalloc-128, kmalloc-256, kmalloc-512,
kmalloc-1k, kmalloc-2k, kmalloc-4k, kmalloc-8k

调用 kmalloc(size, GFP_KERNEL) 时：

  • 若 size ≤ 8KB：从对应的 slab 缓存分配
  • 若 size > 8KB：直接调用 buddy allocator (alloc_pages)

12.7.4 Vmalloc — 非连续物理内存的连续虚拟映射

vmalloc(size)
  → 在 vmalloc 虚拟地址空间找一个 size 大小的空洞
  → 逐页调用 alloc_page(GFP_KERNEL) 获取单个物理页（不要求连续）
  → 逐页修改页表 (PGD → P4D → PUD → PMD → PTE)
  → 返回连续的虚拟地址

与 kmalloc 的区别：

13. BIOS 硬件探测深层原理

本章详细阐述 BIOS 在启动时如何发现每种硬件——探测手段、寄存器级操作序列和背后的协议机制。与第 12 章的启动时序对照阅读可获得完整视角。

13.1 探测的核心理念：没有”上帝视角”

BIOS 本身也是一段程序，它没有预先知道接了哪些硬件的能力，必须通过一组标准协议和已知端口地址来主动探测：

探测手段适用对象原理
固定地址 I/O 寄存器芯片组、PIC、PIT、RTC、KBC架构规范锁死了端口号，直接读
CPU 内置指令CPU 自身CPUID / RDMSR / RDPMC
总线协议读寄存器PCI/PCIe、SMBus、LPC按协议发送地址帧，看设备是否应答
命令/响应协议SATA、NVMe、USB发送标准命令，解析返回的数据结构
内存扫描ACPI/SMBIOS 入口在约定地址范围搜索魔法数字签名
探测写回BAR 大小探测写全 1，读回看哪些位被硬件硬编码为 0

BIOS 的探测是层层递进的——先通过 PCI 枚举找到 xHCI 控制器，再通过 xHCI 寄存器操作端口，最后才能发现插了什么 USB 设备。每一步都是根据上一步的发现结果继续深入。

13.2 芯片组探测 — 平台身份的起点

在探测任何外部设备之前，BIOS 必须先知道”自己在什么平台上运行”。芯片组型号决定了后续所有寄存器的基址、初始化顺序和参数表。这一步走错了，整个启动过程全部报废。

13.2.1 物理拓扑：CPU 与 PCH 的互联

现代 Intel x86 平台的物理结构如下：

DMI（Direct Media Interface）是 Intel CPU 与 PCH 之间的私有总线链路，走的是 PCIe 电气层协议但使用专用的链路管理。DMI 3.0/4.0 等效于 PCIe 3.0 ×4 或 ×8。

OPI（On-Package Interconnect）是 DMI 的升级版，物理层相同，但封装内互连延迟更低。

AMD 等效的互连是 Infinity Fabric / GMI，连接 CPU CCD（Core Complex Die）和 IOD（I/O Die，集成了对等的”南桥”功能）。

对 BIOS 而言，探测到的 Device ID 不仅决定寄存器基址，也决定了整个平台的能力集合（如支持的 PCIe 代次、DDR 类型、DMI 链路速度、USB 端口数等）。

13.2.3 前置条件：Cache-as-RAM — 没有内存时如何读 PCI 配置空间

BIOS 探测芯片组的第一个矛盾是：芯片组的寄存器在 PCI 配置空间/MMIO 空间，但 MMIO 的读写需要 DRAM 做地址路由，而 DRAM 此时还没有初始化。

解决方案是 Cache-as-RAM (CAR)：BIOS 在上电后的最初阶段，将 CPU 的 L1/L2 Cache 配置为”不分驱逐写入 RAM 的伪内存”模式（通过设置 MTRR 将一段物理地址标记为 Write-Back 并填满 Cache），用 L1/L2 缓存当临时的栈空间。CAR 模式下，IN/OUT 指令访问 I/O 端口（如 0xCF8/0xCFC）完全不需要 DRAM——这些 I/O 端口事务是直接路由到芯片组的。

BIOS 顺序:
1. CPU 上电, 执行 SPI ROM 中的复位向量
2. 设置 MTRR, 将一段物理地址范围标记为 Cache-as-RAM
3. 直到这一步, 栈建立在 CPU L1/L2 缓存上
4. IN 0xCF8 → 设置 PCI 地址, IN 0xCFC → 读 Host Bridge Vendor ID
   ▲ 这一步不需要 DRAM!!
5. 确定芯片组型号后, 才开始 Memory Training (需要 DRAM 可用)
6. 训练完成后 DRAM 可用 → 切换到正常栈

13.2.4 Host Bridge（BDF 0:0:0）完整寄存器映射

Host Bridge 在 Intel 架构中对应 System Agent（SA）的 PCI 代理，固定在 Bus 0, Device 0, Function 0。BIOS 通过 0xCF8/0xCFC 直接读取。

  0x4C00: 内存训练控制/状态寄存器组

  0x08: DMI Link Status (协商速度、宽带)
  0x20: DMI VC0 资源控制
  0x24: DMI VC0 资源状态

BIOS 探测 Host Bridge 的完整事件序列：

1. 读 BDF 0:0:0, Offset 0x00 → Vendor ID
   ├─ 读到的值:
   │   0xFFFF → Host Bridge 未就绪 (极早期 PCH 还在复位), 等待后重试
   │   0x8086 → Intel 平台
   │   0x1022 → AMD 平台
   │   其他   → VIA/SiS/NVIDIA 等旧平台 (BIOS 可能不支持, 报错)

2. 读 Offset 0x02 → Device ID
   → 遍历 BIOS 内置的 device_id_table:
      struct {
          u16 device_id;
          u8  platform_family;   // 1=Desktop, 2=Mobile, 3=Server
          u8  dmi_version;        // 1/2/3/4
          u8  max_ddr_speed;      // 0=DDR4-3200, 1=DDR5-4800...
          u8  pcie_gen;           // 3/4/5
          u8  usb_ports;          // 总 USB 端口数
          u16 sata_ports;         // 总 SATA 端口数
          u32 mchbar_base;         // MCHBAR 默认基址
          u32 dmibar_base;         // DMIBAR 默认基址
          u32 epbar_base;          // EPBAR 默认基址
          ...
      } platforms[];

   → 匹配成功 → 设置全局 platform 指针, 载入全部基址信息

3. 读 Offset 0x08 → Revision ID (步进)
   → 用于查询 Intel/AMD 的 Specification Update 表
   → 决定是否需要应用特定 Stepping 的 Workaround

4. 读 Offset 0x0E → Header Type
   → bit7=0 (单功能) 或 bit7=1 (多功能 Host Bridge)
   → Header Type & 0x7F == 0 → 标准 PCI Header

5. PCI 扩展能力链表遍历:
   读 Offset 0x34 → CAP_PTR (首次能力偏移)
   while cap_ptr != 0:
       CapID = read_config(BDF, cap_ptr)
       if CapID == 0x09:   记录 PCI Bridge Subsystem Vendor ID
       if CapID == 0x10:   记录 PCI Express 根复合体能力
       if CapID == 0x14:   记录 Advanced Features (ACS)
       cap_ptr = read_config(BDF, cap_ptr+1)

关键：Host Bridge 的 Capability 还描述了有多少个 Root Port——BIOS 在后续 PCI 枚举中需要知道从 Bus 0 的哪些 Device/Function 开始扫描。Intel 平台通过 Host Bridge 的 DEVEN 寄存器（偏移 0x54）和 CAPID0 寄存器（偏移 0xE0）读取 Root Port 的数量和 BDF 分配。

13.2.5 DMI / OPI 链路初探

CPU 与 PCH 之间的 DMI 链路在 BIOS 探测 Host Bridge 时同步初始化。链路的电气训练由芯片组硬件自动完成（类似 PCIe Link Training），但 BIOS 需要读取训练结果来确认连接速度。

DMI 链路初始化流程:
1. Hardware Training (自动):
   - DMI TX/RX 通道自动建立 (接收器检测、速率协商、通道翻转等)
   - 完成后, DMIBAR 偏移 0x08 (Link Status) 生效

2. BIOS 读取 DMIBAR[Link Status]:
   - bit[19:16] = 协商的 PCIe 速率 (1=2.5G, 2=5G, 3=8G, 4=16G GT/s)
   - bit[9:4]   = 协商的通道宽度 (×1/×2/×4/×8)

3. 判断:
   if 协商速率 < 最大能力: 降档运行, 发出 POST Warning
   if 协商速率 >= 8 GT/s: DMI 3.0+ 模式, OK
   if 协商速率 < 5 GT/s: 非常旧平台, 可能不支持

4. 读取 DMIBAR 偏移 0x0C (RCLK Status) 验证 DMA 时钟是否正确

13.2.6 PCH（LPC Bridge / ISA Bridge） — 南桥的 PCI 代理

LPC Bridge 位于 BDF 0:31:0（Intel 平台），Class Code 0x060100（ISA Bridge）。它是 PCH 在 PCI Bus 0 上最重要的设备，内部包含整个 PCH 的核心控制寄存器。

RCBA（Root Complex Base Address）空间是 PCH 另一套重要的寄存器集，通过 MMIO 方式映射，内部包含：

RCBA + 偏移:
  0x0000: RCBA 版本 ID
  0x1000: PCH 芯片组配置寄存器
  0x2000: HPET 配置
  0x3000: GPIO 配置
  0x3100: GPIO 路由
  0x3400: LPC 桥配置 (COM/LPT/KBC 解码)
  0x3418: LPC 通用解码范围 1
  0x3500: Flash Protection Range 寄存器 (BIOS Range Write Protect)
  0x3800: I/O 解码基址 (已废弃, 现在用 0x80-0x87 替代)

BIOS 探测 LPC Bridge 的完整事件序列：

1. 读 BDF 0:31:0, Offset 0x00 → Vendor ID
   ├─ 0xFFFF → PCH 不存在或未就绪 (ERROR!)
   └─ 0x8086 → 继续

2. 读 Offset 0x02 → Device ID (PCH 型号)
   → 从 PCH ID 表获取:
      - PCH 家族 (如 Z790/B760/H770/Q670)
      - USB 端口数量和类型分布
      - SATA 端口数量
      - PCIe Lane 数量
      - ME/CSME 固件版本范围

3. 读 Offset 0x40 → PMBASE
   → 验证 ACPI PM 寄存器可读写
   → 读 PMBASE + 0x0C → PM_TMR (24 位 ACPI 定时器) 验证 ACPI 计时是否工作

4. 读 Offset 0x60 → RCBA
   → 通过 MMIO 地址访问 RCBA 空间
   → 读 RCBA+0x0000 → 验证 RCBA 版本

5. 读 Offset 0x80 → LPC_GENERIC_DEC_RANGE1
   → 检查哪个范围被 BIOS 预解码给 EC/KBC
   → 若需要, 重新编程

6. 读 Offset 0xA0 → BIOS_CNTL
   → bit1 == 1 → BIOS Locked! (只能通过硬重启解锁)
   → bit5 == 1 → SMM 写保护已开启

7. 遍历 Bus 0 上 PCH 固定 BDF 表:
   for each (dev,func,pch_device_name) in pch_bdf_table:
       vid = read_config(0, dev, func, 0x00)
       if vid != 0xFFFF:
           记录该设备存在
           若 DID 与预期不同 → 记录为 Silicon 变体, 更新平台结构体
       else:
           若该设备在 Datasheet 中标为 "必须存在" → POST Error!
           若标为 "可选" → 跳过

13.2.7 PCH 内部关键功能模块的探测

确定了 PCH 型号后，BIOS 依次初始化 PCH 的各个内部模块。以下列出需要特别处理的关键设备：

SPI Flash Controller (BDF 0:31:5)：

这是 BIOS 访问自身存储的唯一通道。PCH 内 SPI 控制器直接连接到主板上的 SPI Flash 芯片。
BIOS 在探测阶段不需要"重新初始化" SPI 控制器（因为 CPU 是通过 PCH SPI 直接从 Flash
取指令的），但需要:

1. 读 SPI BAR0 → 确定 SPI 寄存器 MMIO 基址
2. 读 Flash Descriptor 区域 (Flash 的首个 4KB Sect):
     - 签名 0xFF0A (Intel Flash Descriptor)
     - Flash 布局 (BIOS/ME/GBE/Platform 数据区域的大小)
     - Master Access 权限 (CPU/ME 对各区域的读写权限)
3. 检查 Flash Descriptor 的 VSCC (Vendor Specific Component Capabilities)
     → 确定 Flash 的 JEDEC ID 和指令集 (Write Enable/Erase/Write 所需命令序列)
4. 设置 FREG (Flash Region) 寄存器, 保护 ME 区域防止 BIOS 误写
5. 若发现整个 Flash 被加锁 → BIOS 无法写入自己 → 只能运行不更新微码

MEI / HECI (BDF 0x16:0) — Intel Management Engine Interface：

ME 是 PCH 内一个独立的 ARC/X86 核心，运行完整的 Minix 或 ThreadX 操作系统。
BIOS 需要:
1. 读 BDF 0x16:0 的 BAR0 → MEI MMIO 基址
2. 通过 MEI 协议 (HECI / MEI Bus) 发送 "DRAM Init Done" 消息
3. ME 返回: 加密引擎状态、固件版本、PCH 的 Fuse 状态
4. 向 ME 请求 End-of-POST 消息 → ME 知道引导过程到了哪步

SMBus 控制器 (BDF 0:31:4)：

这在前文 SPD 读取时已经使用。BIOS 在此处:
1. 读 BAR0 → SMBus I/O 基址
2. 验证 Host Status 寄存器可读写
3. 设置 SMBus 时钟频率 (通常 100kHz)

GPIO Communities：

PCH GPIO 是平台最复杂的配置之一，每个引脚可独立配置为 GPIO/原生功能。
BIOS 需要:
1. 从 LPC Bridge 读 GPIOBASE → 得 GPIO 社区 0 的 I/O 基址
2. 每个社区包含:
     - GPIOCFG (配置寄存器): 功能选择 (GPIO/原生1/原生2/原生3)
     - GPIOROUTE: IOxAPIC / SCI / SMI / NMI 路由选择
     - GPIOTXSTATE: 输出值
     - GPIORXSTATE: 输入值
3. 遍历所有 GPIO 社区 (通常 4-12 个社区, 每个社区最多 32 个引脚)
4. 根据平台配置表将关键引脚设置为正确模式:
     - M.2 SATA/PCIE Select → 原生功能
     - BIOS Recovery → GPIO 输入
     - 主板 ID Strapping → GPIO 输入 (读主板版本)

13.2.8 AMD 平台差异

AMD 平台在 Broadcom (2017+) 的 Zen 架构后采用了与 Intel 不同的物理结构，但 BIOS 访问的方式一致——都通过 PCI 配置空间读 Host Bridge (BDF 0:0:0) 来判断平台。

AMD 平台读 BDF 0:0:0:
  Vendor 0x1022 → AMD
  Device ID:
    0x1450 → X370  (Zen 1)
    0x1480 → X470  (Zen+)
    0x14B5 → X570  (Zen 2/3 IOD)
    0x14D8 → B650  (Zen 4)

AMD 没有传统 LPC Bridge（因不使用 Intel 的 PCH 而是自家 FCH/整合 IOD），但 BIOS 仍通过 PCI 枚举发现 FCH 内部的 SMBus、SATA、USB 等设备（BDF 地址集不同）。

13.3.1 CPUID 硬件工作机制

CPUID 不依赖外部总线。CPU 微码内部维护了一组 Model-Specific 值寄存器，指令解码器按（EAX, ECX）组合从 200+ 个只读 MSR 中选择返回数据写入 EAX/EBX/ECX/EDX。

0x80000001-Long Mode / NX / SYSCALL / 1GB Pages 能力

13.4 内存探测详解：SMBus 寄存器级流程

SPD（内容已在 12.2.2.1 介绍）通过 SMBus（I²C 物理层）读取。BIOS 上电后通过 PCH 内的 SMBus 主机控制器逐个访问 DIMM 插槽。

13.4.1 DDR 内存架构

现代 x86 的内存控制器（IMC）已集成在 CPU 内部：

CPU 封装
  ├── Core Complex (CCX)                   → 计算核心
  ├── System Agent (SA)                    → PCIe 根复合体 + 显示输出
  └── Integrated Memory Controller (IMC)   → 2 通道:
        ├── Channel A → DIMM0, DIMM1
        └── Channel B → DIMM0, DIMM1

13.4.2 SMBus 主机控制器 I/O 寄存器

SMBus 控制器基址由 PCH 固定锁死（通常 I/O 0xEFA0 或通过 PCI BDF 0:31:4 的 BAR0 确定）：

SMBus 主机控制器寄存器 (I/O 基址 + 偏移):
  偏移 0x00: HST_STS  (Host Status)      — INTR/BUSY/FAILED...
  偏移 0x02: HST_CNT  (Host Control)     — START/BYTE_DATA...
  偏移 0x03: HST_CMD  (Host Command)     — EEPROM 偏移地址
  偏移 0x04: XMIT_SLVA (Transmit Slave Addr) — DIMM 地址 (0x50-0x53)
  偏移 0x05: HST_D0   (Host Data 0)      — 数据低字节

BIOS 读取 SPD 的寄存器级流程：

for each slave_address in {0x50, 0x51, 0x52, 0x53}:
    outb(XMIT_SLVA, (slave_address << 1) | 1)  // 7位地址 + R/W=1
    outb(HST_CMD, 0x00)
    outb(HST_CNT, 0x48)                         // START + BYTE_DATA
    等待 HST_STS.BUSY=0
    if HST_STS.FAILED == 1: continue  // 该插槽无 DIMM

    for offset in range(0, spd_size):
        outb(HST_CMD, offset)
        outb(HST_CNT, 0x48)
        等待 HST_STS.BUSY=0
        spd_data[offset] = inb(HST_D0)

13.4.3 Memory Training 硬件实现

SPD 只提供说明书上的时序参数，但每个 DIMM 插槽到 CPU 的走线长度不同，Memory Training 是自动校准电气参数的过程。BIOS 并非亲自收发 DDR 信号，而是设置 IMC 寄存器让 IMC 硬件自动执行：

训练项目的做法
DQS 门控训练找到数据选通脉冲的有效采样窗口用 DRAM MPR 读回已知数据，逐步延迟 DQS 采样点
Write Leveling补偿 IMC→DRAM 的飞行时间差异DRAM 用 CK 边沿采样 DQS，IMC 逐步延迟 DQS 沿
Read/Write DQ Deskew补偿 8 条 DQ 线之间的时滞每条 DQ 独立延迟，写已知模式读回找 eye 中心

13.5.3 深度优先枚举算法

全局变量: next_bus = 1

enumerate_bus(bus):
  for device = 0 to 31:
    for function = 0 to 7:
      Vendor ID = read_config(bus, device, function, 0x00, 2)
      if Vendor ID == 0xFFFF: continue   // 设备不存在

      Header Type = read_config(..., 0x0E, 1)
      Class Code  = read_config(..., 0x09, 3)

      // 遍历扩展能力链表 (Capability List)
      CapPtr = read_config(..., 0x34, 1)
      while CapPtr != 0:
          CapID = read_config(..., CapPtr, 1)
          if CapID == 0x10: 记录 PCI Express 能力 (Link/Dev Cap/Status)
          if CapID == 0x05: 记录 MSI
          if CapID == 0x11: 记录 MSI-X
          CapPtr = read_config(..., CapPtr + 1, 1)

      if (HeaderType & 0x01) == 0x01:    // PCI-PCI 桥
          secondary_bus = next_bus++
          write_config(..., 0x18, secondary_bus)
          enumerate_bus(secondary_bus)    // 递归!
          write_config(..., 0x19, next_bus - 1)  // 回填 Subordinate

BAR 大小探测：写 0xFFFFFFFF 到 BAR → 读回 → 低几位为 0 的部分即硬件锁定的”请求地址大小” → 低bit0=1 表示 I/O BAR，bit[2:1]=10 表示 64bit MMIO BAR（跨两个寄存器）。

13.6 传统 I/O 设备

有些设备不需要 PCI 枚举——I/O 端口地址由 PC 架构锁定。

13.6.1 8259 PIC（可编程中断控制器）

固定端口：Master 0x20/0x21，Slave 0xA0/0xA1。BIOS 通过 ICW1-ICW4 命令字初始化和验证。写 0x11 到 Master 端口 → 设置中断向量基址 → 验证 OCW1 屏蔽寄存器可读写。

13.6.2 8254 PIT（可编程间隔定时器）

固定端口：0x40/0x41/0x42/0x43。BIOS 写控制字→写分频值→读回计数验证递减。基准频率 1,193,182 Hz。

13.6.3 RTC/CMOS（实时钟）

固定端口：0x70/0x71（bit7 控制 NMI）。BIOS 读 0x0D bit7 判断 CMOS 电池有效性，读 0x00-0x09 验证 BCD 格式时间。

13.6.4 8042 键盘控制器（KBC）

固定端口：0x60（数据）、0x64（命令）。BIOS 等待 IBF=0，发 0xAA 自检命令，预期返回 0x55。若超时无返回说明无 KBC（较新平台已移除），改用 USB 键盘。

13.6.5 Super I/O 芯片与 LPC 总线

Super I/O 挂在 LPC 总线上，集成 UART/并口/GPIO/硬件监控/看门狗。BIOS 操作流程：

outb(0x2E, 0x87); outb(0x2F, 0x87)   // 进入 PnP 配置模式
outb(0x2E, 0x20); chip_id = inb(0x2F)  // 读 Chip ID
// 使能串口 UART#1:
outb(0x2E, 0x07); outb(0x2F, 0x02)    // LDN=2 (串口)
outb(0x2E, 0x30); outb(0x2F, 0x01)    // 使能
outb(0x2E, 0x60); outb(0x2F, 0x03)    // 映射到 0x3F8
outb(0x2E, 0xAA)                       // 退出配置模式

13.7 存储设备探测

13.7.1 SATA AHCI 设备识别

PCI 枚举 Class 0x0106 → AHCI 控制器。每个物理端口通过 ABAR（BAR5）映射的 HBA 寄存器区独立管理：

Port 0 寄存器 (偏移自 ABAR):
  0x100: PxCLB  (Command List Base Address) → 指向命令头表
  0x108: PxFB   (FIS Base Address)          → 指向 FIS 接收区
  0x12C: PxSSTS (Serial ATA Status)         → DET=3 表示设备已连接
  0x130: PxSCTL (Serial ATA Control)

探测流程:
  PxSSTS & 0x0F == 3 → 设备存在
  分配 CLB 和 FB → PxCMD.ST=1 启用 DMA
  构建 Command Table → H2D FIS (Command=0xEC Identify Device)
  PxCI=1 启动命令 → 等待中断完成
  解析 512 字节 IDENTIFY 数据 → 型号、序列号、LBA48 容量

13.7.2 NVMe 设备识别

PCI 枚举 Class 0x0108 ProgIF 0x02 → NVMe 控制器。通过 BAR0 MMIO 寄存器空间操作：

NVMe 寄存器 (BAR0):
  0x14: CC   (Controller Configuration) → EN 位
  0x1C: CSTS (Controller Status)        → RDY 位
  0x24: AQA  (Admin Queue Attributes)   → SQ/CQ 条目数
  0x28: ASQ  (Admin SQ 基址, 64位物理地址, 4K 对齐)
  0x30: ACQ  (Admin CQ 基址, 64位物理地址, 4K 对齐)

初始化流程:
  CC.EN=0 → 等待 CSTS.RDY=0
  分配 ASQ/ACQ (各 4K 对齐) → MR(AQA) → MR(ASQ) → MR(ACQ)
  CC.EN=1 → 等待 CSTS.RDY=1
  构建 SQ Entry (OPC=0x06 Identify, PRP[0]=输出缓冲)
  写 SQ Tail Doorbell → 等待 CQ Entry
  解析结果: 序列号、型号、固件版本、Namespace 数量
  Identify Namespace (CNS=0) → 容量、LBA 大小

13.8 USB 控制器与设备枚举

USB 是 PCI 枚举的下游：先通过 PCI Class/Sub 识别控制器类型，再操作控制器寄存器访问下游设备。

0x0C030x10OHCIUSB 1.1 (12Mbps)MMIO, HCCA 共享内存

13.8.2 xHCI 端口探测与地址分配

1. 控制器初始化:
   停止 HC → 分配 DCBAAP/Command Ring/Event Ring → 启动 HC

2. 端口探测:
   for port in 1..MAXPORTS:
       PORTSC = MR(0x400 + port*0x10)
       if PORTSC.CCS == 1:  // 设备已连接
           写 PORTSC.PP=1 (上电) → PR=1 (复位) → 等待 PED=1

3. 地址分配:
   发送 Enable Slot 命令 → 获得 Slot ID
   写 Input Context (Slot + EP0, MaxPacketSize=8)
   发送 Address Device 命令 → 获得 USB 设备地址

4. 读取设备描述符:
   Doorbell EP0: Setup Packet 80 06 00 01 00 00 08 00
   返回: bcdUSB, bDeviceClass, bMaxPacketSize

5. 用真实 MaxPacketSize 重新发送 Address Device

上图展示的是一条严格的分层递进链路，自上而下分为四个层级：

第一层 · 复位入口 — CPU 上电后从 0xFFFFFFF0 取第一条指令，执行 SPI ROM 中 BIOS 的复位向量代码。此时没有内存、没有设备信息，唯一可用的是 CPU 内部的 L1/L2 缓存（Cache-as-RAM）作为临时栈。

第二层 · 芯片组识别 — BIOS 做的第一件事是通过固定 BDF 0:0:0（Host Bridge）和 0:31:0（LPC Bridge）读 PCI 配置空间，获取 Vendor/Device ID。这一步确定平台型号后，后续所有设备的寄存器基址、初始化参数表才有据可查。若此步失败，BIOS 无法继续。

第三层 · 五路并行探测 — 芯片组就绪后，五条探测线路同时展开：

  • CPUID 走 CPU 内部指令通道，不依赖外部总线，直接读出型号、缓存拓扑、特性标志和核心数
  • SMBus 通过 I²C 协议访问每个 DIMM 插槽上的 SPD EEPROM，获取内存条容量和时序参数，随即触发 IMC 硬件执行 Memory Training 使 DRAM 可用
  • PCI/PCIe 通过 0xCF8/0xCFC 或 ECAM 遍历全部 BDF 空间，深度优先枚举所有桥和终端设备，读出 Vendor ID / Device ID / Class Code，并为每个设备分配 BAR 地址空间和 MSI/MSI-X 中断向量
  • 固定 I/O 按 PC/AT 遗留端口号直接访问 PIC、PIT、RTC，写命令字后读回验证设备存在
  • LPC 总线 通过 0x2E/0x2F 端口进入 Super I/O 芯片的 PnP 配置模式，依次使能所需的传统外设

第四层 · 数据汇总 — 五路探测完成后，探测到的全部信息汇入三张标准表交给操作系统：E820 表描述物理内存布局（哪些地址可用、哪些被硬件占用）；ACPI 表（MADT/MCFG/DSDT/SRAT/DMAR 等）描述设备树、中断路由、NUMA 拓扑和 IOMMU 映射；SMBIOS 表（Type 0/1/2/4/7/17 等）提供人类可读的硬件资产清单。操作系统通过这些表获取全部硬件信息，开始构建自己的设备模型和驱动框架。
